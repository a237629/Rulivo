# 第 10 步验收记录

## 范围

本步实现基于角色的权限控制和管理操作审计：

- `USER`：普通用户基础角色。
- `SUPPORT`：客户支持角色。
- `ANALYST`：分析角色。
- `ADMIN`：管理角色。
- 管理员修改用户角色时，在同一数据库事务中写入 `audit_logs`。

未实现第 11 步的交易领域模型。

## 权限规则

- 每个新用户在注册或第三方登录时自动获得 `USER`。
- 一个用户可以同时拥有多个角色。
- `/admin/**` 接口必须通过登录认证并拥有 `ADMIN`。
- 角色替换必须保留 `USER`。
- 管理员不能移除自己的 `ADMIN`。
- 系统不能移除最后一个管理员的 `ADMIN`。
- 停用用户即使持有有效会话也不能继续访问受保护接口。

## 管理 API

所有接口都要求 Bearer access token 和 `ADMIN` 角色。

| 方法  | 路径                            | 说明                         |
| ----- | ------------------------------- | ---------------------------- |
| `GET` | `/admin/users/:userId/roles`    | 查询指定用户角色             |
| `PUT` | `/admin/users/:userId/roles`    | 原子替换指定用户角色并写审计 |
| `GET` | `/admin/audit-logs?take=1..100` | 按时间倒序查询审计记录       |

角色替换请求示例：

```json
{
  "roles": ["USER", "SUPPORT", "ANALYST"]
}
```

## 数据库变化

迁移 `20260727000400_step_10_rbac_audit`：

- 新增 `Role` 枚举：`USER`、`SUPPORT`、`ANALYST`、`ADMIN`。
- 新增 `user_role_assignments` 多角色关联表。
- 新增 `audit_logs` 审计表及行为人、目标用户、操作类型和时间索引。
- 为迁移前已有用户补写 `USER`。
- 为 `audit_logs` 添加数据库触发器，拒绝应用直接执行的 `UPDATE` 和所有 `DELETE`，保持记录不可变；仅允许 PostgreSQL 外键在用户删除时将引用置空。

审计记录保存行为人和目标的标识快照，因此用户被删除后仍可追溯。角色变更与审计写入处于同一事务，不会出现只改权限而漏记审计的情况。

## 管理员初始化

本地和测试环境的 seed 会为固定演示用户写入 `USER` 与 `ADMIN`。生产环境不提供公开的“首个管理员”接口；首个管理员应由受控部署或数据库运维流程配置。

## 验收项

- 普通 `USER` 调用管理接口返回 HTTP 403。
- 添加 `ADMIN` 后可查询和修改用户角色。
- 角色变更后数据库保存完整角色集合。
- 同一事务生成 `USER_ROLES_REPLACED` 审计记录。
- 审计记录包含 request ID、行为人、目标、变更前和变更后角色。
- 数据库拒绝篡改或删除审计记录。
- 管理员不能移除自己的 `ADMIN`。
- Prisma schema、迁移、OpenAPI、lint、typecheck、测试、构建和格式检查全部通过。
